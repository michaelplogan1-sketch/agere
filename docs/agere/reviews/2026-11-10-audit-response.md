## A frontier fallback is a recovery route, not an accuracy theorem

**[inferred]** I reject the statement that a frontier fallback guarantees accuracy cannot fall below frontier alone. Wrong scope, an omitted source, a mistaken attribution rule, a dropped date restriction or a stale intermediate value can contaminate the fallback before the model sees the question. A pipeline can also incorrectly accept a cheap answer and never invoke fallback. Shared model family agreement does not eliminate that risk; existing code and FMEA explicitly recognize it (E20–E24).

**[inferred]** Keep one capable Sonnet/Opus investigator over the same governed native tools as the eventual fallback, with the unchanged original question and explicit shared decision context. Let deterministic operators do cohort membership, sums, denominators, windows, joins and contractual calculations; use models for interpretation that actually requires them. Validate the selected route, dispatch, execution, claim binding and final saved/displayed result. Do not route every query through frontier merely to create the appearance of an accuracy floor.

**[taken from a receipt]** There is a concrete reason to preserve this division: E33 reconciles **20 output rows / 260 cells / 16 payer groups**, **23,169 counted payer claims**, **23,853 cash allocation records**, and **587 negative allocations**, retaining unknown currency and rejecting the old provider-amount basis.
