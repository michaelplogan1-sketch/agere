## 1. Person identity

### 1.1 Verdict

1. There is no crosswalk in `raw/` from any source identifier to the manifest `patient_ids` (`P-`, `SYN-`, `WHP-`). Searches of the whole `raw/` tree for `P-1001`, `P-HF01`, `P-2289`, `P-9047`, `SYN-001C49DB-BE3`, `SYN-0039FCF3-30E`, `001C49DB`, `0039FCF3`, `WHP-` and 20 `WHP` suffixes returned zero hits. The manifest ids exist only in `manifest.json`; the mapping to them sits in the sealed `private/` keys (not opened). From `raw/` alone a manifest id can be reproduced only as a membership count, never looked up per person.
2. Agere must mint its own person key. The evidence supports doing so deterministically in three tiers (1.4). Measured: the union of normalized (last name, first-name token, DOB) across every feed is 4,179 keys, against 4,113 manifest patients (the 66-key excess is name/format variants and duplicate charts, see 1.5).
3. Counts line up with the three id families: the Epic deep-chart panel has 1,614 patients, and 111 `P-` + 1,503 `SYN-` = 1,614 (inferred: those two families are the deep-chart panel). The other 2,499 (`WHP-`) are the payer/practice population (inferred).

### 1.3 Identifiers that are the same value across feeds (deterministic joins)

- MBI: CCLF fixed, CCLF CSV, enrollment, ALR, MSSP programs, MSSP X12, MSSP NCPDP, SDOH (Medicare rows), and the 834 member id for payers 0/1/2 `MEDICARE_FFS` are the same 11-char value. Measured: all 287 `MEDICARE_FFS` 834 member ids are in CCLF8 (287/287). CCLF8 holds 566 MBIs; ALR assigns 273.
- Practice MRN: Epic `identity_id.identity_id` = athena `PATIENT.enterpriseid` = eCW `patients.hl7Id` = FHIR `Patient.identifier.value` = HL7 ORU PID-3.1. Measured: 718 of 718 distinct ORU MRNs exist in the EHR/FHIR MRN set, and all 691 ORU demographic keys exist in the EHR set. MRN format by source/practice: `ICE-<ST>-<n>-<7 hex>` (most), `CE-CA-11-<7 hex>` (practice `WHN-PRACTICE-CA-11` consistently drops the leading `I`: athena 347 rows, FHIR 359 rows, ORU 876 messages), 16 hex (EPIC-DEEPCHART and `fhir_bulk/DEEPCHART`), `E` + 7 digits (EPIC-CA after go-live). The practice is recoverable from the MRN (`ICE-CA-5-...` = `WHN-PRACTICE-CA-5`; ORU authority `PRACCA5`).
- Payer claim ids and payer member ids are shared by flat extracts, X12 837/835/834, NCPDP and care-gap files of the same payer (see section 2).

### 1.4 Resolution method (every feed to one person)

Tier 0, source-native key (never merge on it across sources): Epic (instance, `pat_id`); athena (`contextid`, `patientid`); eCW (practice, `pid`); FHIR (practice folder, `Patient.id`); payer (payer folder, `MEMBER_ID`); CMS (MBI).

Tier 1, deterministic cross-source within a practice (MRN join):
- `mrn = Epic identity_id.identity_id | athena enterpriseid | eCW hl7Id | FHIR identifier MR | ORU PID-3.1`; qualify with the practice (practice code embedded in the MRN, instance folder, contextid, FHIR practice folder, ORU PID-3.4 authority).
- Epic `identity_id.line` + `identity_type_id` identify the issuing practice. In EPIC-DEEPCHART a single `pat_id` can have two MRNs (549 of 1,614 patients), one per practice (example below).
- FHIR `Patient.id` stays constant when the MRN changes at an EHR go-live, so it bridges old and new MRNs (example below).

Tier 2, deterministic bridge from CMS to payer feeds: the MBI is the 834 member id for `MEDICARE_FFS` loops of WH-PAYER-0/1/2, the CCLF/ALR key, and the member id in MSSP X12/NCPDP. Medicare Advantage / dual / commercial / Medicaid members (WH-PAYER-MA1/2/3, DSNP1, C1/2/3, MCD1/2, X1) carry payer-assigned ids, with no MBI anywhere in their files.

Tier 3, demographic match (required to connect EHR to payers to CCLF to ADT to SDOH):
- Key: normalized `lower(last_name)`, first token of `lower(first_name)`, DOB (ISO). Confirm with sex and ZIP5 or address. Name sources: EHR `first_name`/`last_name`, 834 `NM1*IL`, payer eligibility, CCLF8 `bene_1st_name`/`bene_last_name`, ALR, SDOH, HL7 PID-5 `LAST^FIRST`, care-gap `MemberName` ("First Last"). DOB sources: EHR `birth_date`/`dob`/`dobdatetime`/`birthDate`, payer `DOB`, 834 `DMG*D8`, CCLF `bene_dob`, ALR `bene_brth_dt` (MM/DD/YYYY), HL7 PID-7 (YYYYMMDD).
- Measured coverage of the demographic key across feeds: ADT 1,322 of 1,354 person keys exist in the payer/CCLF sources and 425 in the EHR set; 1,441 of the 1,614 deep-chart persons appear in payer/CCLF sources; 3,885 of 3,947 payer-side persons are in two or more payer-side feed types; deep-chart persons (1,614) and practice-level EHR persons (807) overlap on 0 keys.
- Fields available for matching, by feed: Epic/athena/eCW/FHIR (name, DOB, sex, address, ZIP, phone in Epic/athena/eCW users), payer eligibility (name, DOB, gender, address, city, state, ZIP), 834 FULL (name, DOB, sex, address, city, state, ZIP; CHG files have the same loop), CCLF8 (name incl. middle, DOB, sex code, race, address lines, ZIP5, ZIP4, county FIPS), ALR (name, DOB, sex, state/county), SDOH (name, DOB, ZIP), HL7 ADT/ORU PID (name, DOB, sex, street, city, state, ZIP), care-gap files (name, DOB).
- No demographics at all (id only): ncpdp (DOB + gender + cardholder id), X12 835 (member id only; no name), programs risk files (DOB + sex + member id), 837 (name + DOB + sex + member id).

Recommended order: (1) group source records by tier 0 key; (2) merge sources of a practice by MRN (tier 1); (3) merge MBI and payer ids through the demographic key when the identity is one of tier 2's cases; (4) merge across practices/payers/hospitals by demographic key, requiring name, DOB and (sex or ZIP5) agreement; (5) keep the match evidence as the audit trail.

Gotchas:
- MBI re-issue (5 beneficiaries): CCLF8 shows two MBIs for one person with contiguous `bene_rng_bgn_dt`/`bene_rng_end_dt` (e.g. Ann Rivera 1952-09-24: `2H51Q97FQ99` 2026-09-01..2028-06-16, then `2HBCAB84FC1` from 2028-06-17). CCLF9 lists only the new MBI (`crnt_num`) with `prvs_id_obslt_dt` equal to the new start date and leaves `prvs_num` blank, so the old-to-new link must come from demographics and contiguous spans. `bene_hic_num` is blank everywhere; MBI is the only Medicare id.
- Duplicate member ids inside one payer: 308 payer-plus-demographic-key combinations carry more than one `MEMBER_ID`, 284 with identical ZIP+address (e.g. WH-PAYER-MCD2, Julie Johnson 2000-08-16, 6448 Main St 97233: `MCD286C2678E6`, `MCD23A0B6A661`, `MCD2DA237233F`, each with its own subscriber id). No subscriber id is shared by two members (0 of 3,360), so `SUBSCRIBER_ID` is not a household key. A person can also hold ids at several payers (716 persons in two or more payers, including COB and Medigap).
- Epic and CMS sex codes differ: Epic `sex_c` 1 Female, 2 Male, 3 Unknown (`zc_sex`); CCLF `BENE_SEX_CD` 1 Male, 2 Female; ALR `bene_sex_cd` 1/2 the CMS way, MSSP QALR and risk files use `M`/`F`; payer `GENDER` `M`/`F`; eCW `users.sex` `male`/`female`; HL7/834 `M`/`F`; NCPDP C5 1 male, 2 female.
- Zero padding: CCLF fixed width pads `CUR_CLM_UNIQ_ID` to 13 (`0364628236918`), `CLM_LINE_NUM` to 10, `BENE_AGE` to 3, county code to 3; the CSV strips them (`364628236918`, `1`, `78`, `15`). Normalize before comparing the two CCLF copies.
- Names carry mojibake and appended text in malformed rows (a cp1252 byte for `e-acute`, e.g. `Rene` followed by that byte appended to a status or id field: Epic `identity_type_id` `5942Renée`, payer `NETWORK` `OUTRenée`). Decode as cp1252/latin-1, not UTF-8.
- Date-of-birth formats differ per feed (section 4). Epic `birth_date` ISO; athena `dob` ISO; eCW `users.dob` ISO; FHIR `birthDate` ISO; payers per-payer; 834 `D8`; CCLF ISO; ALR `MM/DD/YYYY`; ORU/ADT `YYYYMMDD`; SDOH ISO.
- Implausible demographics exist (e.g. WH-PAYER-MA1 `MEDICARE_ADVANTAGE` 834 loop for Gabriel Carter with DOB 2027-07-23, WH-PAYER-MA2 member Ann Rogers DOB 2019-11-08), so run DOB/product plausibility checks before using DOB as a hard key.

### 1.6 What cannot be resolved deterministically

- Hospital ADT (`L-<ST>-<n>-<8 hex>` MRNs, authority `HOSPxx`): none of the 1,753 distinct ADT MRNs equals any EHR MRN (0 matches). ADT persons resolve only by demographic key. The visit number in PV1-19 (`WHN-E-3bb011c22cbecbad687f`) appears in no other feed.
- Payer-to-EHR: no id is shared between payer files (member id) and EHR/FHIR (MRN). Demographic key only. Only 686 of 2,203 payer-eligibility persons (and 2,142 of 3,720 834 persons) have a demographic match in the EHR set, which is expected (many members are claims-only).
- Medicare Advantage/commercial/Medicaid members to MBI: not linkable except through demographics.
- Any feed to the manifest `patient_ids`: not resolvable from `raw/` (1.1).

## 4. Feed-by-feed inventory

### 4.1 cms_cclf (fixed width, CMS CCLF IP v43)

- Hierarchy: `cms_cclf/<YYYY-MM>/P.A9999.ACO.ZC<1-9>Y<yy>.D<yymmdd>.T<7 digits>`. The folder is the reporting month; the file date `D<yymmdd>` is the delivery date (folder `2026-09` holds `D261012`, delivered 2026-10-12; manifest `sender` `CMS`). `ZC1`..`ZC9`, one of each per month, 44 monthly folders 2026-09..2030-04. Variants: `_RESEND` (5 files), `_v2` (4 files, replace the original of the same name), 64 zero-byte files (CCLF3 and CCLF6 are routinely empty; some others are header-less empties delivered by mistake).
- Format: fixed width, no delimiter, no header row, LF, one record per line, layout in `references/formats/cclf_layouts_v43.json` (appendix A2). Dates `YYYY-MM-DD` (10 chars); numerics zero padded; mostly ASCII, rare cp1252 bytes in names.
- File kinds, grain, volume: CCLF1 Part A claim header (47 CSV columns; grain claim; 4,426 lines), CCLF2 Part A revenue-center lines (grain claim line; 6,373), CCLF3 Part A procedure (always empty), CCLF4 Part A diagnosis (grain claim x diagnosis, `clm_val_sqnc_num`, `clm_poa_ind`; 12,004), CCLF5 Part B physician lines (grain claim line, 55 columns incl. up to 12 diagnoses; 54,181), CCLF6 Part B DME (104), CCLF7 Part D (grain fill; 17,679), CCLF8 beneficiary demographics (grain beneficiary x month; 21,755), CCLF9 MBI crosswalk (112).
- Claim types (`clm_type_cd`): Part A 10, 20, 40, 50, 60 (hospital outpatient 3,731, inpatient 429, home health 66, SNF 57, hospice 21 in CSV CCLF1); Part B 71; DME 82; Part D 1.
- Codes: ICD-10-CM undotted (`I10`, `R0789`, `S72001A`) with `dgns_prcdr_icd_ind` 0; HCPCS/CPT in `clm_line_hcpcs_cd` + `hcpcs_1..5_mdfr_cd`; revenue codes 4-digit (`0320`); MS-DRG `dgns_drg_cd`; NPI in `*_npi_num`; MBI; NDC 11 digits `clm_line_ndc_cd`; POS `clm_pos_cd` (21, 11, 81); no CARC (CMS carrier denial code `clm_carr_pmt_dnl_cd` 1, `clm_prcsg_ind_cd` A in all rows).
- Corrections/voids: `clm_adjsmt_type_cd` 0 original, 1 cancellation (negative amounts, Part A `clm_org_cntl_num` = original `clm_cntl_num`), 2 adjustment (Part B). Part B also carries `clm_disp_cd` 01 / 03 (cancelled) / 02 (adjusted). `cur_clm_uniq_id` changes with every version; the stable chain key is `clm_cntl_num` characters 9-18 (hex tail). Example chain for one Part B line (all three `clm_cntl_num` end in the same 10 hex characters `5F3E59A15E`): original `202609285F3E59A15E` (cur id `1140113798487`, $112.57), cancel `202610235F3E59A15E` (cur id `9754075328292`, -$112.57, adj 1), re-issue `202610235F3E59A15E` (cur id `1522418913441`, +$112.57, adj 0). Measured: Part A cancellations 59 of 4,304; Part B 1,529 type 1 and 863 type 2 of 51,423; Part D adj 1 429 of 19,122; DME 1 + 1 of 107.
- Date fields: `clm_from_dt`, `clm_thru_dt`, `clm_line_from_dt`, `clm_efctv_dt`, `clm_idr_ld_dt` (load date drives incremental ordering), `bene_dob`, `bene_rng_bgn_dt`, `bene_rng_end_dt`, `bene_death_dt`.
- Person id: MBI only (`bene_hic_num` blank). Delivery defects seen: `_RESEND`, `_v2`, empties.

### A10. ncpdp D.0 observed field dictionary
Separators: 0x1C field separator, 0x1D group separator, 0x1E segment separator, LF between claim records (CRLF in header/trailer lines).
- File header line: `00` FS `T<9 digits>` FS `<YYYYMMDD delivery date>` FS `D0` FS `<payer id>`; trailer line: `99` FS `<claim record count>`.
- Claim record: `G1` FS `<claim id WHN-RXC-...[-R]>` GS then transaction header (fixed text): BIN(6) version(2)=`D0` transaction code(2) `B1`|`B2` processor control number(10, space padded) transaction count(1) service-provider-id-qualifier(2)=`01` service-provider-id(15, NPI left aligned, space padded) date-of-service(8 YYYYMMDD) RS.
- AM04 insurance: C2 cardholder id, C1 group id. AM01 patient: C4 DOB (YYYYMMDD), C5 gender (1 male, 2 female). AM07 claim: EM prescription/service reference qualifier (1), D2 Rx number, E1 product id qualifier (03), D7 NDC (11 digits), E7 quantity (3 implied decimals, e.g. 30000 = 30), D3 fill number (0 = original), D5 days supply, D8 DAW. AM03 prescriber: EZ qualifier (01), DB prescriber NPI. AM11 pricing: D9 ingredient cost, DC dispensing fee, DU gross amount due.
- AM21 response status: AN transaction response status (P paid, R rejected, A approved for B2 reversal), FA reject count, FB reject code (observed 70 product/service not covered, 79 refill too soon, 75 prior authorization required). AM23 response pricing: F5 patient pay amount, F9 total amount paid. AM87 appears on 158 records (not decoded).
